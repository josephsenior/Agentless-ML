# Recorded regression-test selection

The controller can now build a regression schedule from a trusted test inventory
and a recorded exclusion response. This follows the direction in the pinned
Agentless `select_regression_tests.py`: begin with tests passing on the original
revision, then exclude tests whose expectations may change with the intended fix.
It is not a relevance ranking that keeps only tests close to the edited code.

## Inputs and execution

Pass `regression_tests` to `FixedWorkflowController`: a tuple of `RegressionTest`
records, each pairing a unique, single-line `test_id` with a trusted
`PublicTestCommand`. Supply `RecordedStageResponses.regression_exclusions` as
exact IDs, one per line, optionally fenced. An empty string means exclude none;
`None` means the stage is not enabled.

Each inventory command runs on a fresh checkout of the pinned, unpatched source.
Passing IDs become the selection prompt's inventory. Ordinary failures are
recorded but not eligible; timeout, harness and other infrastructure failures
stop the run rather than silently shrinking the inventory.

The response can only exclude known passing IDs. Unknown IDs and prose are errors,
not commands. Duplicates are harmless, and inventory order determines execution
order. The remaining regression commands are followed by any caller-supplied
reproduction commands. This schedule is frozen before candidate validation and
used for every localization and repair sample.

Do not mix inventory-based regression selection with fixed regression commands.
That would make it unclear which regression checks the response can exclude.
Without an inventory, older fixed schedules work unchanged. If exclusions leave
no validation commands at all, the controller stops explicitly. With reproduction
commands remaining, reproduction-only validation is allowed and documented in
the saved schedule.

## Why this boundary

Test execution stays in the existing runner; source adapters do not acquire test
runner dependencies. IDs map to commands supplied by the controller, never to
shell strings generated by a model. This is usable across languages, but callers
still need to supply the inventory. Automatic discovery and framework-specific
test-report parsing are not implemented by this milestone.

One inventory entry is one command-level selection unit. Use a command targeting
one test if you want individual-test selection; naming a whole suite with a test
ID does not turn its exit status into individual test results. Runner exit-code
declarations must distinguish assertion failures from collection or import errors.
The baseline is one observation, not a flakiness analysis.

The prompt and strict parser are local multilingual implementations. Upstream's
parser ignores unknown lines, and its prompt-length fallback truncates the passing
list. We reject unknown IDs and do not silently truncate. These differences and
the strict empty-schedule policy need review before claiming upstream parity.

## Evidence

`regression-baseline.json` records IDs, trusted commands, baseline results,
workspace provenance and log locations. `regression-selection.txt` is the prompt;
`regression-selection.json` records passing, excluded and retained IDs. The final
schedule is in `controller.json`; the recorded response is also retained in
`responses.json` when selection fails.

[Parser tests](../tests/test_regression_selection.py) check exclusion semantics,
empty responses, duplicates and invalid IDs. [Controller tests](../tests/test_fixed_workflow.py)
check unpatched baseline execution, the identical candidate schedule, pre-existing
failures, unknown exclusions, infrastructure failures and empty schedules. These
tests use a controlled runner; they do not establish live Docker or benchmark
coverage for this new stage. There are no model calls.

Next is reproduction-test generation and its checks. Full benchmark test
discovery, official scoring and live sampling remain separate integration work.
