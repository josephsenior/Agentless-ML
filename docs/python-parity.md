# Python parity with Agentless v1.5.0

The Python implementation is developed against Agentless v1.5.0 at revision
`b150f28465a77a81a7f4776384957a4271f5bd69`. Parity is checked at observable
boundaries instead of inferred from similar code.

## What is covered

The current fixtures cover the path from Python source to the focused context
that would be passed to the repair stage:

- class, function, and direct-method names and line spans;
- source-line capture and discovery order;
- default and indentation-preserving skeletons;
- compression of long assignments;
- filtering and rendering of the project tree;
- file- and symbol-localization prompts;
- parsing complete, incomplete, and labelled fenced responses;
- association and ordering of returned locations;
- class, method, function, variable, and line resolution;
- context-window calculation and selected-source rendering.

The real-repository fixture is based on SWE-bench Lite instance
`psf__requests-2317`, dataset revision
`6ec7bb89b9342f664a54a6e0a6ea6501d3437cc2`, and Requests revision
`091991be0da19de9108dbe5e3752917fea3d7fdc`. It contains the filtered 82-file
Python tree and the prompt-visible representation of `requests/sessions.py`.
The selected repair context uses the options shown in the published reproduction
instructions: `--loc_interval`, `--context_window=10`, and `--diff_format`.

## Why there are two Python representations

`legacy_symbol_projection()` exists only as a regression seam. It reproduces
several behaviors that we do not want to turn into multilingual design rules.
`PythonAdapter.parse_file()` produces the normalized Agentless-ML structure used
by new code.

This distinction matters because the published parser:

- omits async definitions from its AST-derived structure, even though they
  remain visible in LibCST skeletons;
- can report a nested function as if it were top-level;
- can omit a top-level function when its name matches a class method;
- merges root-level files and an immediate same-named package into one tree node.

The golden fixtures preserve these effects wherever they change model-visible
context. The normalized representation keeps lexical nesting, includes async
definitions, and uses repository-relative paths.

## How the fixtures are produced

The JSON files in `tests/fixtures/python/` are generated by the scripts in
`tools/`. They include the upstream revision and source hash. We also recapture
the real-repository fixtures independently and compare them byte for byte before
accepting them.

This is deliberately narrower than claiming identical end-to-end behavior. The
model is not called by these tests, and no gold patch is used.

## Repair and selection boundary

The next parity boundary now covers:

- byte-compatible Python repair-prompt assembly for the published diff-format
  condition;
- generated SEARCH/REPLACE parsing and atomic in-memory application;
- deterministic multi-file Git patch construction;
- patch normalization and voting;
- regression/reproduction filtering and deterministic reranking.

The exact retained behavior and intentional multi-file and safety changes are
listed in [Repair and selection](repair-selection.md). Model execution, public
test runners, and benchmark verification remain outside the parity claim. The
recorded controller has since exercised three SWE-bench Pro Python tasks. Those
smoke runs do not extend the upstream parity claim. See the
[replication map](replication-map.md) for differences and unfinished behavior.
